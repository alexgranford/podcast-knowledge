# Comparing podcast text models

Use this when the user asks whether another text model can replace the current podcast composer, or requests a smaller head-to-head after an end-to-end failure. Keep benchmark artifacts outside the production notes folder; never change the default model to run a comparison.

## End-to-end test, when requested

1. For existing episodes, choose contrasting jobs with `asr/transcript-v1.json` and `source/resolved-episode-v1.json`; verify duration, transcript word count and baseline note. Reuse their transcripts. For a genuinely fresh episode, resolve and acquire audio inside the isolated benchmark, run ASR **once**, save its transcript, then give every text model that identical artifact; do not transcribe per model.
2. Copy the existing transcript and metadata, or stage the newly resolved episode, in per-job benchmark directories under `/workspace`; use isolated `PODNOTE_ROOT` and `PODNOTE_STATE` with a copied show registry and vault metadata profile/catalogue. Add benchmark model IDs only to the isolated catalogue after verifying them against the live model server. Point `PODNOTE_CACHE` to the shared production cache for existing jobs, or link the isolated cache's model-arbiter directory to the shared arbiter for fresh jobs; verify that `model_arbiter.local_model_session` serializes loading with the queue in either layout. Do not write to production notes or mutate its show registry.
3. Run `podnote.py --job-dir <staged-job> --model <exact-id> --force` *once per model per job*, sequentially, from the installed skill or the exact patched checkout being evaluated; label which code ran and separately verify any later installation. Checkpoint stdout, exit status, time, generated note and SHA256 after each run. Save each model's note to a model-specific result path immediately because the next `--force` run overwrites the shared benchmark note path; pass `--force` on that next run even if the first model completed. Do not infer completion from cached part files: require exit 0, `NOTE:`, `STATUS: complete`, and a validated note. Inspect the **last** error as well as cached parts: generation may finish while cleanup raises before note validation and writing. Separate ASR/acquisition time from synthesis-only time, and mark warm part/synthesis caches; never present unlike total runtimes as a model speed ranking.
4. If cleanup fails after all parts are cached, check loaded-model status and the arbiter lease before doing anything else; reconcile only when no other model session owns the lock, then verify unloaded state and cleared lease. For a *diagnostic only*, reconstruct from cached sections/themes/summary in the isolated root with model calls explicitly disabled, run the note validator, and save separately. Record any cache misses (including a metadata/tag fingerprint altered by a registry update); never let an offline reconstruction silently make new model calls or present it as a completed `podnote.py` run. If the user explicitly requests manual completion of an HTTP 202 asynchronous unload case before a fix exists, use a benchmark-only wrapper around the installed runner that changes only the unload transition: accept 202 only after bounded status polling confirms `loaded=false` under the shared arbiter lock. If the user separately asks for a durable fix, patch and test the repository client first, then benchmark using that patched code rather than the wrapper; install only when requested or otherwise authorized. Label resumed content caches warm and confirm `NOTE:`, `STATUS: complete`, validator pass, note hash, and unloaded/lease-free server state.
5. Read the transcript alongside results. Score coverage of explicit proposals, figures, speaker attribution, forecast-versus-fact discipline, note structure, completion and cost; cite concrete omissions or distortions. Baseline notes may contain later verification additions, so distinguish those from model-authored text before ranking quality or word counts. A failed full run is a *compatibility result*, not proof of intrinsic model weakness. Verify loaded-model status and lease against the active residency policy when the test ends; an intentionally retained text model is not itself stale cleanup.

## Targeted part-note comparison

When a full episode fails or the user wants actual text from every model:

1. Select a few short (roughly 300–500-word) verbatim transcript passages covering different reasoning demands; save source job IDs, exact text and word offsets. Give every model the *same* compact, task-representative prompt: one topic line, 4–6 specific bullets, preserve numbers/hedges, do not invent speakers or facts.
2. Make calls sequentially under the shared oMLX model arbiter. Save exact prompt, response text, HTTP status and JSON keys, `finish_reason`, `usage.completion_tokens`, `reasoning_content` length, and elapsed time per passage/model. Never print credentials. A nominal HTTP 200 without `choices` is not a usable completion; record its response shape instead of indexing blindly.
3. If a model returns `length` or leaks a self-instruction monologue, distinguish visible final text from reasoning tokens. An `enable_thinking=False` request is not evidence that the server disabled thinking; check `reasoning_content` and token usage. Try a **documented** simpler completion-first prompt and larger cap on the *same excerpt* in the isolated harness, saving original and adapted attempts. Do not accept truncated text as a production note or quietly change shared pipeline limits. If a controlled variant succeeds, label the comparison as non-identical prompts.
4. Compare the full resulting text, not only latency or bullet count. A concise model can omit one of several explicit arguments; a fluent model can turn a forecast into fact or conflate two populations in a statistic. Report sample size, warm/cold conditions, and whether the test covered only part notes versus themes, summary, metadata validation and complete-note writing.

A benchmark can justify further model-specific adaptation; promotion requires an uncached complete-note test that meets the existing completeness and vault-validation gates. When a repository fix is also installed locally, test the installed copy and report PR/merge, installed-file, and already-running-process states separately: a process started before installation can still hold the old code in memory. Match the user's current language rather than inheriting a previous task's output language.
